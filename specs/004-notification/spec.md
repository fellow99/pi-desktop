# 004 — 原生通知（notification）功能规格

> **Module:** 004-notification（原生通知）  **Status:** Proposed  **Last Updated:** 2026-10-12  **上游基线:** pi v1.1.0 / pi-web v0.11.1
> **对应方案:** [`./plan.md`](./plan.md)
> **实现落点:** `src/main/notifications.ts`、`src/main/session-watch.ts`
> **规划依据:** `docs/工程规划.md` §5.4、§4.8、§9.3、§11.2 O1、§11.1 R7

## 1. 模块概述

### 1.1 目的

通知模块的职责是：**在窗口不可见/未聚焦时，用系统原生通知告知用户「一轮任务已完成」或「出错了」**。由于 `pi-web` 的事件只通过 SSE 暴露给渲染层、主进程**没有**现成的事件钩子，本工程的 v1 事件源确定为**主进程尾随会话 JSONL 文件**（✅ 决策 §5.4、§11.1 R9 的零补丁路线）。

### 1.2 解决的问题

- **用户不盯窗口**：agent 任务耗时较长，用户切走后无法感知任务何时结束。
- **主进程无事件钩子**：`pi-web` 无 WebSocket，事件下行是 SSE（只在渲染层可订阅）；要在主进程拿到事件必须另辟事件源。
- **零补丁约束**：不得为「拿事件」去改上游或 import 上游内部模块（升级即失效，⚠️ §5.4 备选②）。
- **不打扰**：窗口在前台时弹通知是纯噪音；同一会话的连续事件会形成通知风暴；应用启动时把历史消息全部补弹更不可接受。
- **隐私**：会话内容属于用户数据，通知与日志都不得携带正文。

### 1.3 范围

**包含**

- 会话文件尾随（`<agentDir>/sessions/**/*.jsonl`）：增量读取、偏移推进、新文件发现、截断/轮转容错。
- 事件识别：一轮任务正常完成、一轮任务出错、会话信息变化（名称）。
- 通知策略：仅在窗口不可见/未聚焦时弹、同会话冷却去重、启动基线（不补弹历史）。
- 平台细节：Windows 通知归组依赖 AppUserModelId（由 007 设置）。
- 度量与留痕：事件类型、通知次数、延迟（供 P0-5 取证）。

**不包含**

- 通知的持久化、历史记录、免打扰时段策略。
- 审批请求类通知（`pi-web` 的审批交互只在 UI 内；主进程无事件源）。
- 通知内交互按钮与点击后的深链/会话跳转（v1 最多唤回窗口）。
- 渲染层主动上报事件的备选通道（需引入壳层 IPC；见 `plan.md` §3.1 的备选登记）。
- 更新的可用性提示 → 011-release-update。

## 2. 用户故事

- 作为用户，我希望把窗口切到后台后，agent 完成一轮任务时收到系统通知，以便知道可以回来了。
- 作为用户，我希望任务出错时收到一条明确的失败通知，并知道去哪里看详情。
- 作为用户，我希望窗口就在前台时**不要**弹通知（我自己看得见）。
- 作为用户，我希望同一个会话的连续事件不要刷屏（短时间内只提醒一次）。
- 作为用户，我希望应用刚启动时不要把昨天/上次会话的历史消息全部补弹出来。
- 作为隐私敏感用户，我希望通知里只有会话名与状态，不含对话内容。
- 作为用户，我希望关掉通知能力时应用其它功能不受影响（失败不阻塞）。

## 3. 功能需求

动作词：**MUST** 必须满足；**MUST NOT** 禁止；**SHOULD** 建议；**MAY** 可选。

### 3.1 事件源（会话 JSONL 尾随）

- FR-004-001：系统 MUST 以主进程尾随 `<agentDir>/sessions/**/*.jsonl` 作为**唯一**事件源。**MUST NOT** 为拿事件而修改上游、也不得 import `pi-web` 的内部事件模块。
- FR-004-002：系统 MUST 增量读取（按文件维护字节偏移），**MUST NOT** 每次扫描都全量重读文件。
- FR-004-003：系统 MUST 处理三类文件变化：新增会话文件（新偏移从 0 或文件末尾基线开始）、追加（从上次偏移继续）、截断/轮转（当前大小 < 上次偏移时重置偏移）。
- FR-004-004：单行 JSON 解析失败时，系统 MUST 跳过该行并记录 WARN；**MUST NOT** 中断尾随、MUST NOT 输出该行内容。
- FR-004-005：系统 MUST 结合 `fs.watch` 与定时兜底扫描（默认间隔 `SESSION_WATCH_INTERVAL_MS`）工作，**MUST NOT** 只依赖 `fs.watch` 的事件投递（不同平台语义不一致）。
- FR-004-006：系统 MUST 在应用退出时停止尾随（关闭 watcher、清定时器），不阻塞退出链。

### 3.2 通知策略

- FR-004-007：系统 MUST 仅在主窗口不可见**或**未聚焦时发出通知；窗口在前台可见且聚焦时 MUST NOT 发通知。
- FR-004-008：系统 MUST 对同一会话在冷却窗口内去重（默认 `NOTIFICATION_COOLDOWN_MS`）。
- FR-004-009：系统 MUST 在启动时先做一次基线扫描：只记录各文件的初始偏移，**MUST NOT** 为基线之前的既有内容发通知。
- FR-004-010：一轮任务正常完成时，通知 SHOULD 使用「会话 <名称> 已完成」文案；一轮任务以错误结束时，SHOULD 使用「出错了，请查看应用详情」类文案。
- FR-004-011：会话名称不可得时，系统 SHOULD 退化使用会话 id 的短后缀标识，**MUST NOT** 使用会话内容作为标识。
- FR-004-012：系统 MUST NOT 把会话正文、工具参数、模型输出写入通知标题/正文；日志中同样 MUST NOT 出现会话内容。

### 3.3 平台与标识

- FR-004-013：Windows 上系统 MUST 依赖已设置的 AppUserModelId（由 007-app-entry 在就绪后早期设置）以保证通知正确显示与归组。
- FR-004-014：通知点击行为：v1 MAY 唤回主窗口；**MUST NOT** 触发任何数据面动作（不跳转会话、不执行命令）。
- FR-004-015：通知能力不可用（用户关闭系统通知、Linux 无通知服务）时，系统 MUST 记录 WARN 并继续运行，**MUST NOT** 阻塞启动或抛错。

### 3.4 可观测性

- FR-004-016：系统 MUST 记录尾随统计（发现文件数、新增行数、识别到的事件数、发出通知数）与通知延迟（事件时间戳 → 通知发出时间），供 P0-5 与后续调优取证。
- FR-004-017：事件源目录不存在或不可读时，系统 MUST 记录 WARN 并保持静默（不弹通知、不重试风暴），且 MUST NOT 阻塞启动。
- FR-004-018：日志统一前缀 `[pi-desktop]`，且 MUST NOT 输出密码/凭据/会话内容。

## 4. 关键实体

| 实体 | 说明 | 关键属性 |
|---|---|---|
| 会话尾随器（SessionWatcher） | 主进程侧增量读取器 | `agentDir`、`offsets: Map<filePath, number>`、`baselineDone: boolean`、`timer`、`watchers` |
| 尾随事件（TrailingEvent） | 从 JSONL 行识别的语义事件 | `kind: 'turn-complete' \| 'turn-error' \| 'session-info'`、`sessionId`、`sessionName?`、`at: number`（事件时间戳） |
| 通知决策（NotificationDecision） | 是否允许弹 | `allowed: boolean`、`reason: 'foreground' \| 'cooldown' \| 'ok' \| 'no-source'` |
| 通知记录 | 会话级冷却表 | `Map<sessionId, lastNotifiedAt>` |
| 通知正文 | 平台展示文本 | 标题 = 产品名；正文 ≤ 一行（会话名 + 状态） |

## 5. 验收场景

### 场景 S1：后台完成通知

- Given 应用已启动（基线扫描完成）且主窗口处于后台（最小化或未聚焦）
- When 用户发起一次真实对话并让 agent 完成一轮
- Then 系统发出原生通知，正文含会话标识与「已完成」语义

### 场景 S2：前台不打扰

- Given 主窗口可见且聚焦
- When agent 完成一轮任务
- Then **不发出**任何通知

### 场景 S3：冷却去重

- Given 同一会话在冷却窗口（默认 10 s）内连续完成两轮
- When 第二轮的完成事件被识别
- Then 只发出一次通知（第二次被冷却丢弃，且决策原因记录为 `cooldown`）

### 场景 S4：启动不补弹历史

- Given `<agentDir>/sessions/` 下已有大量历史会话文件
- When 应用启动并完成基线扫描
- Then 不发任何通知；只有基线之后新增的行才会触发通知

### 场景 S5：出错通知

- Given 窗口在后台
- When 尾随识别到一轮任务以错误结束
- Then 发出「出错了，请查看应用详情」类通知（不含错误正文中的会话内容）

### 场景 S6：容错

- Given 某会话文件被 CLI 截断重写（大小小于上次偏移），或存在半行/损坏 JSON
- When 尾随继续
- Then 截断被识别并重置偏移、损坏行被跳过并 WARN，尾随不中断、无异常抛出

### 场景 S7：事件源缺失不阻塞

- Given `<agentDir>/sessions/` 不存在（全新用户）
- When 应用启动
- Then 记录 WARN、不弹通知、应用正常进入首屏

## 6. 非功能需求

- **性能**：尾随 MUST 为固定内存（只保留偏移与行缓冲）；单次扫描开销与新增字节数成正比，**MUST NOT** 随文件总量增长（历史会话可能很大）。
- **延迟**：通知延迟（事件落盘 → 通知）SHOULD 在秒级；⬜ 实测值由 P0-5 记录（§11.2 O1）。
- **可靠性**：`fs.watch` 事件丢失时由定时兜底补偿；解析失败不中断；目录消失不崩溃。
- **隐私**：通知与日志均不含会话正文；事件负载只保留标识与时间戳。
- **平台**：Windows/macOS/Linux 三平台使用系统通知；不可用时降级为静默 + WARN（§9.3 台账）。
- **资源**：停止尾随后 MUST 释放所有 watcher 与定时器（不得阻止进程退出）。

## 7. 假设与约束

- **假设（✅ 已核实）**：会话格式为行式 JSONL，落在 `<agentDir>/sessions/`，目录名为 `<cwd 编码>`、文件名为 `<timestamp>_<session-id>.jsonl`（version 3）。依据：`docs/工程规划.md` §2.1（`pi` 的 `src/config.ts` 与 `durable` 会话存储）。
- **假设（🔶 沿用「零补丁」纪律）**：JSONL 是上游的稳定对外产物（CLI 与 pi-web 共用），比内部模块 API 更适合作为壳层事件源。
- **约束**：⬜ 会话落盘的**写入时机**（turn 结束一次性写 vs 流式增量追加）与「完成/错误」在行中的具体标识形态**尚未实测**，必须由 P0-5 探针定标（§5.4、§11.2 O1）。在探针出结论前，本模块**不得**把某种行结构写成硬编码假设。
- **约束**：`pi-web` 与 `pi` CLI 并发写同一会话 JSONL 不受上游支持（⚠️ R7）。本模块**只读**，因此不加剧该风险；同时 MUST NOT 打开文件进行写入或加锁。
- **约束**：⬜ 是否能找到「更干净的上游钩子」（例如渲染层浏览器事件上报）属 P0-5 的评估项；若采用则需引入壳层 IPC，并需更新本规格（条目只追加不修订）。
- **约束**：通知不作为「审批未决」的提醒通道（v1 无事件源）。

## 8. 依赖

**上游（被本模块消费）**

- 008-runtime-config：`agentDir`（会话目录根）。
- 002-window：`getMainWindow()` 与窗口可见性/聚焦状态（决策输入）。
- 007-app-entry：AppUserModelId 设置、启动/退出编排（初始化与停止尾随）。

**下游（消费本模块）**

- 007-app-entry：在宿主就绪后启动尾随，在退出链中停止。
- （间接）003-tray：与通知共享「宿主状态」语义，但不互相调用。

**外部**

- `node:fs`（`watch`、`open`、`read`）、`node:path`、Electron `Notification`、操作系统通知中心（Windows 需 AppUserModelId，Linux 依赖桌面环境，macOS 走通知中心）。
