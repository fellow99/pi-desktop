### 0.4 非目标（本版明确不做）

- **不 fork `pi` / `pi-web`**：对上游只做幂等补丁（本版预计 **0 条**，见 §7）。

- **不做深链/自定义协议、开机自启、全局快捷键**：Phase 2 视需求评估。

## 1. 项目概述

### 1.1 一句话定义

把 [Pi](https://pi.dev)（可扩展的 agent harness）与其浏览器界面 [Pi Web](https://github.com/agegr/pi-web) 封装成 **Windows / macOS / Linux 的一等公民桌面应用**：用官方 Electron 43 承载 **`pi-web` 的 Next 服务器（含 agent 与 `/api`）**，渲染层同源加载该服务端提供的 Pi Web UI，桌面壳补齐 pi 自己没有的东西（托盘、原生通知、单实例、窗口状态、首启产物引导、更新引导），最终产出三平台可分发安装包。

**应用名 / 可执行名 / 应用 ID**：**`Pi Desktop`** / `pi-desktop` / `com.fellow99.pi.desktop`（⬜ 应用 ID 与发布主体归属需人工确认，见 §11.3）。

### 1.2 关键结论速览

| 维度 | 结论 | 出处 |
|---|---|---|
| 目标形态 | 三平台 Electron 桌面应用（Windows 主验证） | §1.1、§4.1 |
| 工程组织 | `pi-workspace` **submodule 并行容器**，`../pi`、`../pi-web` 源码引用 | §6.1 |
| 骨架来源 | 复制 `dsh-desktop` 的工程框架与构建/发布骨架后改造 | §6.1、§6.3 |
| 上游基线 | `pi` **v1.1.0** + `pi-web` **v0.11.1** | 文档头 |
| 运行时 | Electron **43.7.9**（Node 24.21.0 / Chromium 150 / ABI 148） | §4.4 |
| 服务端宿主 | **主进程进程内嵌入 Next 服务器**（无子进程、无孤儿） | §4.2 |

### 1.3 与两个参考工程的关系

| 参考工程 | 关系 | 复用内容 |
|---|---|---|
| `dsh-desktop` | **方案模板**（同型：Electron 桌面壳 + 进程内宿主 + 同源渲染） | 工程骨架、`specs/` 编号与文档骨架、Forge/vite/Fuses 配置形态、CI/Release 流水线形态、托盘/通知/窗口/单实例的实现范式 |
| `pi-desktop-hos` | **同族已验证实现**（同上游、同宿主形态、不同平台） | 进程内 Next 启动入口与回退策略、`tar-extract.js`（流式 ustar 解压）、预览密钥轮换与双凭据注入、启动阶段机与 fail-visible 纪律 |

**关键差异**：`dsh-desktop` 的宿主是 dsh 自己的 `runProfile('desktop')`；本工程的宿主是**上游 `pi-web` 的 Next 服务器**（只做装配，不改上游）。`pi-desktop-hos` 面对的平台约束（loopback 隔离、子进程 `exit` 不送达、无 PTY、无 git）**在桌面全部不存在**，因此本工程**恢复**了终端、MCP stdio、OAuth 回环、git/worktree 等能力（§9.3）。

### 1.4 上游身份声明

本工程名称含 `pi`。`Pi` 是上游开源项目（MIT，`earendil-works/pi`），`Pi Web` 是其社区浏览器界面（MIT，`agegr/pi-web`）。本工程是二者在**桌面平台**上的第三方封装，与上游作者无隶属关系，未获其背书。README 与应用内「关于」必须据此注明，并声明「不 fork、只装配」。

## 2. 背景

### 2.1 `pi`（宿主：CLI + SDK）

- **是什么**：最小、可扩展的 agent harness。monorepo（`pi/packages/`），全部包 lockstep **1.1.0**，根 `package.json` 声明 `engines.node >= 22.19.0`（✅）。
- **包结构**（✅）：`coding-agent`（CLI + SDK + 扩展系统，**核心依赖**，bin `pi` → `dist/bundle/cli.js`）、`ai`（多 provider LLM API）、`agent-core`（agent 运行时）、`tui`（终端 UI 库）、`durable`（会话持久化，用 `node:sqlite`）、`codemode`（QuickJS/WASM 沙箱）、`mcp`、`protocol`/`client`/`server`（CBOR 协议 + **实验性**服务器）、`chord`、`env`（SSH 远程执行，Rust daemon）、`telemetry`、`evals`。
- **运行形态**（✅）：交互式 TUI、`--print`、`--mode json`、`--mode rpc`（**JSONL over stdin/stdout**），以及**进程内 TypeScript SDK**（`createAgentSession` / `createAgentSessionServices` / `createAgentSessionFromServices` / `SessionManager`，见 `packages/coding-agent/src/index.ts`）。
- **关键事实 A**：`pi` **没有 HTTP 服务模式**（✅ 无 `--port`/`--host`/`--listen` 参数）。`packages/server` 是实验性 Unix socket 路由层，**且要求 POSIX `process.getuid`，Windows 不可用**。
- **关键事实 B**：扩展系统是**进程内加载的 TS/JS 模块**（jiti），无需编译、无独立进程。
- **关键事实 C**：全部状态在一个目录 `~/.pi/agent/`（✅ `src/config.ts`）：`settings.json`、`models.json`、`auth.json`（明文、写入 `0600`）、`mcp.json`、`trust.json`、`extensions/`、`skills/`、`prompts/`、`themes/`、`bin/`、`sessions/`。可经 `PI_CODING_AGENT_DIR` 重定向。
- **会话格式**（✅）：`sessions/--<cwd 编码>--/<timestamp>_<session-id>.jsonl`（version 3 行式 JSONL）。

### 2.2 `pi-web`（UI + 服务端）

- **是什么**：`@agegr/pi-web` **0.11.1**，Next.js **16.3.8** App Router 应用；`engines.node >= 22.19.0`；bin `pi-web` → `bin/pi-web.js`（✅）。
- **形态（本工程的关键前提）**：**一个 Node 进程同时提供 SPA 与 `/api/*`**（✅）。
  - 官方启动：`bin/pi-web.js` → `spawn(process.execPath, [nextBin, "start", "-p", port, "-H", hostname])`，等子进程 stdout 出现 `Ready` 写 run-record 并开浏览器（✅ `bin/pi-web.js:109-146`）。
  - 默认：`--port/-p` 或 `PORT` = **30141**；`--hostname/-H` 或 `PI_WEB_HOSTNAME` = **127.0.0.1**（✅ `bin/pi-web-options.js`）。
  - 无 `output: "standalone"`，**不可静态导出**；生产必须 `cwd = 包目录`（`.next` 固定解析为 `path.join(__dirname,"..",".next")`）。
- **agent 在进程内**：`lib/rpc-manager.ts` 直接 `import` `@earendil-works/pi-coding-agent` 的 SDK —— **不需要 `pi` 二进制在 PATH，也不 spawn `pi`**（✅；`next.config.ts` 的 `serverExternalPackages` 列出四个 `@earendil-works/*` 包）。
- **数据面**：HTTP 上行（`POST /api/agent/[id]` 等 JSON 命令）+ **SSE 下行**（`GET /api/agent/[id]/events` → `text/event-stream`；终端亦为 SSE）。**没有 WebSocket**。
- **启动前必做**（✅）：用随机值重写 `.next/prerender-manifest.json` 的 previewModeId/SigningKey/EncryptionKey（`bin/rotate-preview-secrets.js`），否则 `x-prerender-revalidate` 可绕过 `proxy.ts`；**目录不可写会打印告警并保留已发布密钥**。
- **认证与门禁**（✅ `proxy.ts` + `lib/web-auth.ts` + `lib/request-security.ts`）：matcher `["/","/login","/api/:path*"]`；未设 `PI_WEB_PASSWORD` = **完全无认证**；设置后登录页写 cookie `pi_web_session`（`v1.<exp>.<nonce>.<HMAC-SHA256(密码)>`，30 天），API 客户端可用 `Basic`（用户名固定 **`pi`**）；Host 白名单放行 **IP 字面量**与 `PI_WEB_HOSTNAME`/`PI_WEB_ALLOWED_HOSTS`；Origin + `Sec-Fetch-Site` 校验；失败 401/403/429（登录与 Basic 猜测共用限流）。`/api/web-auth` 免认证（可作探活）。
- **API 规模**：约 90 条路由（`sessions/**`、`agent/**`、`files/**`、`git/**`、`worktrees`、`terminal/**`、`auth/**`、`models/**`、`mcp/**`、`plugins/**`、`skills/**`、`subagents/**`、`cwd/**`、`project-trust`、`web-auth`、`push/**`）。
- **原生依赖**：**只有 `node-pty` 1.2.0-beta.15**（`serverExternalPackages`；`prebuilds/` 内含 darwin/linux/win32 × arm64/x64 目录，✅ 见 §8.2 的 ⬜ 核对项）；**无 better-sqlite3**（会话是 JSONL；`npm ci` 不需要 `electron-rebuild` 之外的编译链）。
- **平台事实**（✅）：Windows 用 `ComSpec||cmd.exe`、POSIX 用 `$SHELL||/bin/sh -l`；macOS 需 postinstall 修 `spawn-helper` 可执行位；路径比较必须走 `lib/paths.ts` 的 `toNativePath()/samePath()`；`git` 缺失时 worktree/diff/文件树降级（不报错）；**唯一 spawn `pi` CLI 的地方是会话 HTML 导出**。
- **壳层扩展点**（✅）：浏览器事件 `pi-web:session-row-contextmenu`（供 Electron 接管会话行右键菜单）；保活注册表 `Symbol.for("@agegr/pi-web/session-liveness/v1")`。

### 2.3 `dsh-desktop`（桌面壳方案模板）

🔶 沿用其结论（读自 `d:/deepseek-harness-workspace/dsh-desktop`）：

- **架构**：Electron **43.0.0** + Forge **^7.11.2** + `@electron-forge/plugin-vite` + `@electron/fuses`；**主进程内跑 dsh Host（webserver + apiProxy + connection）**；渲染进程同源加载 `http://127.0.0.1:<port>/`；**数据面不过 IPC**。
- **外壳能力**：托盘（单例 `Tray` + 菜单）、原生通知（订阅宿主事件流，`turn/end`、`approval/asked`、`agent/error`）、单实例锁 + 第二实例唤回、窗口状态持久化（`window-state.json`，防抖 400ms、`getNormalBounds`、多显示器可见性校验）、F11 全屏、导航加固（`setWindowOpenHandler` 一律 deny + 外链走 `shell.openExternal`）、权限白名单（仅 `clipboard-sanitized-write` + `notifications`，且校验来源与 `webContents.id`）、**常规标题栏**（`frame:true`，无自定义无边框）。
- **安全**：`sandbox: true` + `contextIsolation: true` + **无 `nodeIntegration`**；Fuses 关闭 `RunAsNode`、关闭 `NODE_OPTIONS`/`NODE_CLI_INSPECT`、强制 asar 完整性、`OnlyLoadAppFromAsar`；loopback 并入 `NO_PROXY`/`no_proxy` + `proxy-bypass-list <-loopback>`；系统 CA 合并（`getCACertificates('default'|'system')` → `setDefaultCACertificates`，**能力缺失时安全降级不抛错**）。
- **打包**：`asar: true`、`prune:false`、`derefSymlinks:true`、`executableName`、`extraResource`；makers = Squirrel / ZIP(darwin,linux,win32) / DMG / RPM / DEB。
- **CI**：`ci.yml`（三 OS 矩阵 + `concurrency` 取消在途）与 `release.yml`（tag `v*` 触发，`softprops/action-gh-release` 上传 `*.exe/*.nupkg/*.deb/*.rpm/*.dmg/*.zip`）；**不签名、不公证**。
- **明确不做**：自动更新、原生文件选择器（沿用内置浏览）、全局快捷键、开机自启、多窗口。

### 2.4 `pi-desktop-hos`（同族已验证实现）

🔶 沿用其结论（读自 `pi-desktop-hos/docs/工程规划.md` 与 `src-main/main.js`，1145 行）：

- **进程内 Next 启动入口**：`next/dist/server/lib/start-server.js` 的 `startServer({ dir, hostname, port })` 导出（✅ 本机核对 `pi-web/node_modules/next/dist/server/lib/start-server.js:177` 存在 `async function startServer(serverOptions)`；HOS 侧已实测**宿主不退出**、候选 A 成立），并保留了「按多路径探测导出形态 + 子进程回退」的实现（`src-main/main.js:503-589`）。
- **产物引导**：`src-main/tar-extract.js` 是**真正流式**的 ustar(.gz) 解压器（状态机、固定内存、O(n)；旧实现 O(n²) 曾在真机卡死）；`SHA-256 marker` 幂等（**不是存在性判断**）。
- **凭据注入**（✅ 源码核实）：Basic 头**只在 `/api/*`** 上被校验，页面导航只认 `pi_web_session` cookie → 壳层必须注入**两件**（`session.cookies.set` + `webRequest.onBeforeSendHeaders`）。
- **预览密钥轮换**：直接 `require` 上游 `bin/rotate-preview-secrets.js`（不重新实现），**必须在起服务之前**。
- **实测数据（可作量级参考）**：pi-dist 682 MB / 27,279 文件 → `pi-dist.tar.gz` **115.9 MB**；首启解压与就绪合计约 15 s（真机）。
- **其平台约束在本工程不存在**（因此本工程不需要它的降级面）：loopback 隔离、子进程 `exit`/`close` 不送达、无 PTY、无 `git`/`rg`/`fd`、`symlink` 禁用、`chmod` 静默失效、`/tmp` 不可写、JIT 受限权限。

```
├── pi-desktop-hos/                      # [submodule] 鸿蒙版（独立工程；本工程只复用结论与 2 个模块）
├── pi-desktop-website/                  # [submodule] 官网/下载页（规划中；更新检查的候选数据源）
├── harmonypc-electron/                  # [submodule] Electron-on-鸿蒙 运行时（本工程**不使用**）
└── harmonypc-electron-versions/         # （普通目录，gitignore）鸿蒙运行时归档（本工程**不使用**）
```

**为什么 `pi` / `pi-web` 是 sibling 源码引用而不是 npm 依赖**：
1. `pi-web` 的 `.next` 必须在**本机可再生**地构建（我们要控制 `serverExternalPackages`、裁剪平台无关物、并在打包前完成预览密钥轮换）。
2. 上游 npm tarball 里虽有预构建 `.next`，但它来自 Windows/macOS 的构建机，**无法做目标平台裁剪**（🔶 沿用 HOS 结论）。
3. `pi-web` 依赖 `pi` 的**精确版本 1.1.0**；用 sibling 源码引用可保证两边同源、同版本（✅ `pi-web/package.json`）。

## 3. 目标与原则

**目标**

1. 在三平台提供 `pi` 的**一等公民**桌面应用（对标「`pi` + 浏览器打开 `pi-web`」的桌面体验），而非「包一层浏览器指向 localhost」的粗壳。
2. **100% 复用 Pi Web UI**，不 fork 前端。
3. 核心链路（会话、对话、工具调用、文件读写、终端、模型与凭据配置）端到端可用；**平台/环境差异统一优雅降级且如实可见**。
4. 与 `pi-desktop-hos` 共享同一套上游基线与概念模型，使两个平台的应用行为可对照。

**原则**

1. **零上游改动优先**：先穷尽上游现成机制（环境变量、SDK、配置、既有脚本），再考虑补丁。本版预计 0 条补丁即是这条原则的产物（§7）。
2. **主进程进程内宿主**：服务端跑在 Electron 主进程（Node 24.21），不引入子进程 —— 无孤儿进程、无进程树清理、就绪判定确定。
3. **只写装配代码**：业务逻辑全在上游；本工程写环境装配、产物就位、起服务、建窗、生命周期、桌面能力、构建脚本。
4. **同源数据面**：渲染层只认 HTTP（同源），**零 CORS、零自定义协议、数据面零 IPC**。IPC 仅用于壳层（默认**不需要**，见 §5.6）。
5. **失败可见（fail-visible）**：每个启动阶段必须可观测；不允许「卡住但不说」，也不允许静默降级。
6. **平台差异显式化**：Windows/macOS/Linux 的差异（路径、通知、托盘、可执行名、未签名安装）必须在文档与代码注释里有台账。

## 4. 核心架构方案

### 4.1 选定方案

Electron 主进程（Node 24.21）内：**环境装配 → 产物就位 → 预览密钥轮换 → 进程内启动 Next 服务器（`127.0.0.1:<随机端口>`）→ HTTP 轮询就绪 → `BrowserWindow` 同源加载**该地址。

```
┌─ Pi Desktop（Electron 43.7.9）──────────────────────────────────────────────┐
│  Electron 主进程（Node 24.21.0）                                            │
│    ├─ 环境装配：PI_CODING_AGENT_DIR / PI_WEB_* / NO_PROXY / proxy-bypass     │
│    ├─ 产物就位：pi-dist.tar.gz → <userData>/pi-dist（SHA-256 marker 幂等）    │
│    ├─ rotatePreviewSecrets(<pi-dist>/.next)   ← 必须在起服务之前             │
│    ├─ 进程内 Next 服务器：startServer({dir, hostname:'127.0.0.1', port})     │
│    │     ├─ SPA（Pi Web UI）+ /api/* + SSE /api/agent/[id]/events            │
│    │     └─ agent 会话（pi SDK，**同进程内**，在 globalThis.__piSessions）    │
│    ├─ 就绪判定：HTTP 轮询（**不解析 stdout**，那是 CLI 启动器的做法）        │
│    ├─ 桌面能力：托盘 / 原生通知 / 窗口状态 / 单实例 / 检查更新               │
│    └─ 建窗：BrowserWindow → loadURL('http://127.0.0.1:<port>/')             │
│                              ▲ 同源（无 CORS、无自定义协议）                  │
│    ┌─────────────────────────┴──────────────────────────────────────────┐   │
│    │ 渲染进程（Chromium 150）：标准 Pi Web UI                            │   │
│    │   fetch('/api/*') 上行 · EventSource('/api/agent/[id]/events') 下行 │   │
│    └────────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 服务端宿主形态：主进程进程内（已决策 Q2）

**选定**：在主进程内调用 `next/dist/server/lib/start-server.js` 的 `startServer` 导出（✅ 本机核对存在；🔶 HOS 真机实测宿主不退出、页面/API/SSE 全通）。

| 步骤 | 内容 |
|---|---|
| 1 | `ensureDesktopEnv()`：`PI_CODING_AGENT_DIR`、`PI_WEB_APP_NAME`、`PI_WEB_SKIP_VERSION_CHECK=1`（可选）、`NO_PROXY`/`no_proxy`、`app.commandLine.appendSwitch('proxy-bypass-list','<-loopback>')` |
| 2 | `ensurePiDistExtracted()`：`pi-dist.tar.gz` → `<userData>/pi-dist`（幂等，SHA-256 marker；见 §8.3） |
| 3 | `rotatePreviewSecrets()`：`require(<pi-dist>/bin/rotate-preview-secrets.js)` 后调用（**不重新实现**；缺失即 fail-visible 抛错） |
| 4 | `resolveFreePort()`：`net.createServer().listen(0,'127.0.0.1')` 探测后释放，取高位端口 |
| 5 | `startNext()`：设置 `PI_WEB_HOSTNAME=127.0.0.1`、`PI_WEB_PASSWORD=<随机强密码>`（**起服务之前**），再 `await startServer({ dir, hostname, port })` |
| 6 | `waitForReady()`：HTTP 轮询 `GET /api/web-auth`（免认证探活）或 `/login`，**不解析 stdout**；超时上限 30 s |
| 7 | `createWindow()` + `loadURL('http://127.0.0.1:<port>/')` |

**替换了 `bin/pi-web.js` 的三件事**（必须自己实现，不能依赖它）：① `rotatePreviewSecrets`；② `PI_WEB_HOSTNAME`/`PI_WEB_PASSWORD` 注入；③ run-record（`<agentDir>/pi-web-run/<pid>.json`）—— 本工程**不写 run-record**（那是 CLI 启动的服务器才有的东西）。
**附带收益**：`bin/node-version.js` 的 `>=22.19.0` 硬门禁不经该入口即失效（本工程运行时是 Node 24.21，**门禁本身也已天然满足**，见 §4.4）。

**候选回退 B（登记，不默认启用）**：`child_process.spawn(process.execPath, [nextBin,'start','-H','127.0.0.1','-p',port], { env: { ELECTRON_RUN_AS_NODE: '1' } })` + HTTP 轮询就绪。
**触发条件**（任一成立即启用）：① 探针 P0-1 失败（`startServer` 导出不可用或宿主退出）；② 上游升级后内部入口形态变化且短期无法适配；③ 需要「服务端崩溃隔离/热重启」而产品验收要求它。
**启用代价**（必须登记）：进程树清理（Windows 需 `taskkill /T /F`）、孤儿 `next-server` 占端口、就绪判定改为 stdout + 轮询双路。

⚠️ **必须处理的 Next 关闭语义**（🔶 HOS 结论 + ✅ 上游源码）：`instrumentation-node.ts` 在 `SIGINT`/`SIGTERM` 时先关闭所有 SSE 连接，否则 Next 16 的 `server.close()` **永不退出**。Electron 主进程里我们要自行在 `before-quit` 阶段：置 `isQuitting` → 关闭 SSE（或调用等价钩子）→ `httpServer.close()` → 在 `PI_WEB_SHUTDOWN_DEADLINE_MS`（默认 5000）超时后 `app.exit()` 强退，避免「点了退出但进程不走」。

### 4.3 渲染通道：BrowserWindow 同源（唯一形态）

| 候选 | 说明 | 判断 |
|---|---|---|
| **BrowserWindow 加载 `http://127.0.0.1:<port>/`** | 与 `pi-web` 的认证/Host/Origin/`Sec-Fetch-Site` 校验天然兼容（IP 字面量放行） | ✅ **选定** |
| `file://` 加载静态导出 | pi-web **不可静态导出**（无 `output: 'export'`；有 route handler / SSE / fs / PTY / middleware） | ❌ 不可行 |
| 自定义协议（`app://`） | 会触发 `proxy.ts` 的 Host/Origin 校验 403；且需要改写上游请求基址 | ❌ 不采用 |

**必备项**：
- **渲染层「先 loading 页，再加载真实 URL」**：首次启动要解压产物（数十秒量级），直接加载会长时间白屏（🔶 HOS；本工程首启同样有解压）。
- `window.open` 必须拦截：Pi Web UI 用 `window.open` 打开 OAuth 登录页与会话导出 → `setWindowOpenHandler` 一律 deny，http/https 走 `shell.openExternal`（🔶 dsh 范式）。
- 非安全上下文问题：`http://127.0.0.1` 在 Chromium 里属**可信来源**（loopback 例外），`crypto.subtle`/`localStorage` 均可用；**这一点比 HOS 的 `http://<局域网IP>` 更简单**（⬜ 仍需在 P0-3 里断言，不默认成立）。
- `did-fail-load` / `render-process-gone` 必须记录并可见（fail-visible）。

### 4.4 运行时选型：Electron 43.7.9（已决策 Q4）

| 版本 | 组成（✅ 官方发布矩阵） | 判断 |
|---|---|---|
| 37.2.3 | Node 22.17.0 / Chromium 138 / ABI 136 | ❌ 与 `pi-desktop-hos` 同族，但 Node 22.17 **低于上游 `>=22.19.0`**（HOS 为它专门做了门禁论证） |
| 39.0.0 | Node 22.20.0 / Chromium 142 / ABI 140 | 🔶 备选：贴合上游 engines，但 Chromium 落后两个大版、与 dsh 不同族 |

| **43.7.9** | **Node 24.21.0 / Chromium 150.0.7871.250 / ABI 148** | ✅ **选定**：满足上游引擎要求（含 `node:sqlite`、Next 16 要求）；与 `dsh-desktop`（Electron 43）同主版本，Forge/vite 配置可照搬；含安全补丁 |

### 4.5 网络与安全

| 项 | 方案 | 状态 |
|---|---|---|
| 绑定地址 | **`127.0.0.1`** + 随机高位端口 | ✅ 决策（桌面无 loopback 隔离） |
| UI 访问 | `http://127.0.0.1:<port>/` | ✅ 决策 |
| Host/Origin 门禁 | **无需改写**：`lib/request-security.ts` 对 IP 字面量直接放行；同源请求 Host/Origin 一致 | ✅ 源码核实 |
| 鉴权 | **`PI_WEB_PASSWORD` 默认开启随机强密码**（宿主侧生成、不入日志、不回显） | ✅ 决策 + ✅ 上游机制 |
| 凭据注入（**两件，缺一不可**） | ① 出栈给本服务 host:port 的请求补 `Authorization: Basic pi:<password>`（覆盖 `/api/*` 与 SSE）；② 用同一密码按上游算法派生会话 token 并 `session.cookies.set({ name:'pi_web_session', ... })`（**承载页面导航**，只注入 Basic 会把用户送到 `/login`） | ✅ 源码核实 + 🔶 HOS 已验证 |
| 代理 | `NO_PROXY`/`no_proxy` 追加 `127.0.0.1,localhost`；`app.commandLine.appendSwitch('proxy-bypass-list','<-loopback>')` | 🔶 沿用 dsh |
| 系统 CA | `getCACertificates('default'|'system')` → `setDefaultCACertificates`，**能力缺失时安全降级不抛错** | 🔶 沿用 dsh |
| 渲染进程隔离 | `sandbox: true` + `contextIsolation: true` + **无 `nodeIntegration`** | 🔶 沿用 dsh（本工程同源 HTTP，无需任何 Node 能力进渲染层） |
| Fuses | `RunAsNode:false`、`EnableNodeOptionsEnvironmentVariable:false`、`EnableNodeCliInspectArguments:false`、`EnableCookieEncryption:true`、`EnableEmbeddedAsarIntegrityValidation:true`、`OnlyLoadAppFromAsar:true` | 🔶 沿用 dsh |
| 导航加固 | `setWindowOpenHandler` 一律 deny；`will-navigate` 仅允许同源 + 明确外链白名单；外链走 `shell.openExternal` | 🔶 沿用 dsh |
| 权限白名单 | 仅 `notifications`（+ `clipboard-sanitized-write` 如需），并校验来源 URL 与 `webContents.id` | 🔶 沿用 dsh |
| 本地暴露面 | 绑 loopback + 随机端口 + 随机密码；**不启用 mDNS**；不写入 run-record | ✅ 决策 |
| ⚠️ 待确认 | macOS 上「未签名 DMG + 未公证」会触发 Gatekeeper（右键打开 / `xattr -dr com.apple.quarantine`）；是否接受由 §11.3 决策 | ⬜ |

**为什么密码默认开（而不是依赖 loopback）**：该服务具备**文件读写 + 命令执行（终端/工具调用）**能力；同一台机器上的其他本地进程或已登录的其他用户仍可能访问 loopback 端口。随机强密码 + 双凭据注入的成本已被 HOS 验证过（直接复用其实现），因此默认开启。

### 4.6 目录与数据落点（已决策 Q6）

| 变量/路径 | 目标 | 理由 |
|---|---|---|
| **`PI_CODING_AGENT_DIR`** | 默认 **`~/.pi/agent`**（`os.homedir()`）；设置内可切换 `<userData>/pi-agent` | 桌面版价值是「直接用上你已有的 pi 环境」（凭据/会话/扩展/MCP 立即可见）；隔离模式作为企业/多环境退路 |
| `HOME` / `USERPROFILE` | **不改**（桌面无沙箱） | 与 HOS 的关键差异：那边必须把 HOME 指向沙箱 |

| `pi-dist` | `<userData>/pi-dist/`（由 `pi-dist.tar.gz` 首启解压；marker 文件 `.pi-dist.sha256`） | 可写（密钥轮换的前提） |
| 窗口状态 | `<userData>/window-state.json` | 🔶 dsh 范式（防抖 400 ms、`getNormalBounds`、多显示器可见性校验） |
| 应用日志 | `<userData>/logs/pi-desktop-<YYYYMMDD>.log` | fail-visible：启动阶段、错误栈、版本信息 |

**切换数据目录的语义**（设置项 `agentDirMode: 'shared' | 'app'`，存 `<userData>/pi-desktop-settings.json`）：切换后**必须重启应用**才生效（宿主启动早期就要用到该变量）；UI 提示「切换后应用内会话/凭据与 CLI 的可见性会变化」。**不许**在同一进程内热切换。

### 4.7 启动时序（失败可见）

```
启动 → [lock] 单实例锁（失败即 quit，第二实例唤回主窗口）
   → [env] 环境装配（PI_CODING_AGENT_DIR / PI_WEB_* / NO_PROXY / 代理绕过）
   → [artifact] 产物就位（首次解压 pi-dist.tar.gz；SHA-256 marker 幂等）
   → [secret] 预览密钥轮换（复用上游脚本）
   → [server] 进程内启动 Next（随机端口 + 随机密码）
   → [ready] HTTP 轮询就绪（上限 30 s）
   → [load] loadURL(http://127.0.0.1:<port>/) → 首屏完成 → 关闭 loading 页
       任一阶段失败 → loading 页显示**具体阶段 + 原因**（fail-visible），并写入应用日志
```

规则：统一日志前缀 `[pi-desktop]`；每个阶段在 loading 页可见（阶段文本 + 耗时）；loading 页提供「打开日志」「重试」「退出」三个动作。诊断落点沿用 dsh/HOS 纪律：`globalThis.__hostError` / `__extractError` / `__renderError`。

### 4.8 进程模型与数据流

| 层 | 进程 | 职责 |
|---|---|---|
| 运行时层 | Electron 主进程（Node 24.21.0） | 环境装配、产物解压、**Next 服务器 + agent**、建窗、桌面能力、生命周期 |
| 渲染层 | 渲染进程（Chromium 150） | 同源加载 Pi Web UI；`fetch /api/*` + SSE 订阅 |
| 壳层桥 | （默认**无**） | 数据面不经 IPC；仅当 §5.6 的右键菜单/壳层动作需要时才引入最小 preload 桥 |

**数据流**
- **上行（unary）**：渲染进程 `fetch('/api/<route>')`（同源）→ Next 服务器 → pi-web 路由 → pi SDK。
- **下行（事件帧）**：渲染进程 `EventSource('/api/agent/[id]/events')` → `text/event-stream`（终端同理 `/api/terminal/[id]/events`）。
- **壳层事件源（托盘/通知）**：主进程**尾随会话 JSONL**（见 §5.4），不依赖渲染层、不耦合上游内部模块。

### 4.9 与 `dsh-desktop` 的概念对接

| `dsh-desktop` 概念 | 本工程对应物 | 备注 |

| `runProfile('desktop')`（宿主启动） | **进程内 `startServer({dir,hostname,port})`** | §4.2 |
| `profiles/desktop/`（desktop profile + cordis patch） | `config/` 预置模板 + `agentDirMode` 设置 | pi 无 profile 概念（§6.3） |
| `ctx.connection.authenticatedUrl()`（启动令牌） | `PI_WEB_PASSWORD` 随机密码 + cookie/Basic 双凭据 | 上游自带 |

## 5. 桌面壳能力（v1 范围）

### 5.1 单实例与唤回

`app.requestSingleInstanceLock()` **在最早时机**申请；失败即 `app.quit()`；成功则监听 `second-instance` → 主窗口 `restore() → show() → focus()`。（🔶 dsh 范式）

### 5.2 窗口与状态

- 主窗口默认 **1200×800**，最小 **800×600**（🔶 dsh）。
- **常规标题栏**（`frame: true`）：系统原生最小化/最大化/关闭，不做无边框与窗口控制 IPC（🔶 dsh 已改为此形态）。
- 状态持久化：`<userData>/window-state.json`（尺寸/位置/最大化，防抖 400 ms，`getNormalBounds()`，多显示器可见性校验；异常状态回退默认）。
- `ready-to-show` 后再显示（避免白屏闪烁）；`F11` 切换全屏；`did-fail-load`/`render-process-gone` 记录 + 提示。
- **关窗行为**：v1 = **关窗即退出**（`window-all-closed` → `app.quit()`；对齐 `dsh-desktop`）。若存在运行中的 agent 会话，关窗前给一次确认提示（⬜ 会话运行态的判定来源见 §5.4）。
- macOS：`activate` 且无窗口时重建主窗口；`before-quit` 走优雅关闭链（§4.2 的关闭语义）。

### 5.3 系统托盘

- 主进程内单例 `Tray`（`resources/tray.png`；macOS 用模板图 `trayTemplate.png` ⬜ 待产资源）。
- 菜单：**显示主窗口**、**会话目录**（`shell.openPath(agentDir)`）、**打开日志**、**检查更新**、**退出**。
- 单击图标：Windows/Linux = 唤起窗口；macOS = 弹出菜单（平台惯例）。
- 托盘在**宿主未就绪时也创建**（对齐 dsh 现状），菜单项按就绪态禁用而非消失。
- 退出入口必须走「优雅关闭链」，`destroy()` 托盘后 `app.quit()`。

### 5.4 原生通知（关键设计点：事件源）

**问题**：`dsh-desktop` 的通知直接订阅宿主进程内的 `ctx.on('session/event')`；而 `pi-web` 的事件只通过 **SSE 流**暴露给渲染层，主进程**没有**现成的事件钩子。

**v1 选定方案：会话文件尾随（tail）**
- 主进程 `fs.watch` + 增量 tail `<agentDir>/sessions/**/*.jsonl`，解析新增行（version 3 行式 JSONL），识别「assistant 消息落盘 / 会话信息变化」→ 触发通知。
- 为什么选它：**零上游补丁**、不耦合 `pi-web` 内部模块、**与窗口可见性/渲染进程状态无关**（窗口隐藏或渲染进程重载时通知仍可靠）。
- 通知策略（对齐 dsh 的取舍）：turn 正常完成 → 「会话 <名称> 已完成」；错误 → 「出错了，请查看应用详情」；**避免 noisy**：仅当窗口**不可见/未聚焦**时弹通知（窗口在前台时不弹）；同一会话在冷却窗口（如 10 s）内去重；应用启动后的历史消息**不**补弹（以初始扫描的字节偏移为基线）。
- 平台细节：Windows 需 `app.setAppUserModelId('com.fellow99.pi.desktop')` 才能正确显示与归组；macOS/Linux 走系统通知中心（Linux 需桌面环境支持）。
- ⬜ 待验证（P0-5）：JSONL tail 的通知延迟与可靠性；是否存在更干净的上游钩子（例如渲染层主动上报的浏览器事件）；`pi-web` 会话落盘的写入时机（turn 结束 vs 流式增量）。

**登记备选（不在 v1 启用）**：① 渲染层通过最小 preload 桥上报告警事件（需引入壳层 IPC，见 §5.6）；② 主进程内订阅 `pi-web` 的 SSE/事件模块（**耦合上游内部实现**，⚠️ 上游升级即失效）。

### 5.5 导航加固与外链、权限白名单

见 §4.5 的对应行；实现形态沿用 dsh 范式（`setWindowOpenHandler` + `will-navigate` + `setPermissionRequestHandler` 三处收口，全部校验来源 URL 与 `webContents.id`）。

### 5.6 壳层 IPC 与 preload（默认最小化）

- **默认**：`src/preload/index.ts` 只保留空实现（`export {}`），以维持 Forge/Vite 的 preload 构建目标（🔶 dsh 现状同款）。
- **按需引入**（登记触发条件）：若 §5.4 的 tail 方案不能满足通知及时性，或需要接管会话行右键菜单（`pi-web:session-row-contextmenu` 浏览器事件），则引入**只承载壳层动作**的最小桥（例如 `piDesktop.notify()`、`piDesktop.showContextMenu(rowInfo)`）。**数据面永远不过 IPC**。

### 5.7 检查更新（已决策 Q5 = 半自动）

- 入口：应用菜单/托盘/「关于」页的「检查更新」。
- 行为：查询更新源 → 比较版本（语义化）→ 有新版则弹窗展示版本号与更新说明链接 → `shell.openExternal(<下载页>)`；**不自动下载、不静默安装**。
- 更新源（⬜ 待确认，见 §11.3）：① GitHub Releases API（`https://api.github.com/repos/fellow99/pi-desktop/releases/latest`，注意未认证限流）；② `pi-desktop-website` 提供的静态 feed（官网已作为 submodule 存在，规划中）。
- 失败必须可见且不阻塞：网络不可达时提示「无法检查更新」并在日志留痕。

### 5.8 明确不做（登记）

深链/自定义协议注册、开机自启、全局快捷键、多窗口、无边框自定义标题栏、原生文件选择器（沿用 Pi Web 内置目录浏览）、AI 内容标识（桌面分发无此合规要求）。

## 7. 补丁集

**本版为 0 条必需补丁。**这是一个**结论**而不是省略，逐条登记「为什么不需要」：

| 潜在补丁 | 是否需要 | 理由 |
|---|---|---|
| Node 版本门禁（`>=22.19.0`） | ❌ | 运行时是 Node **24.21.0**（Electron 43.7.9 内置），**天然满足**；且本工程不经 `bin/pi-web.js` 入口 |
| 进程内启动 Next（需内部入口） | ❌ | 使用 `next/dist/server/lib/start-server.js` 的导出，**不改上游文件**；形态变化时走 §4.2 的回退，而不是打补丁 |
| 预览密钥（`prerender-manifest.json`） | ❌ | 直接 `require` 上游 `bin/rotate-preview-secrets.js`（复用其算法与告警行为） |
| 认证/凭据注入 | ❌ | 上游自带 `PI_WEB_PASSWORD` + cookie/Basic 两种凭据；壳层只做注入，不改上游 |
| Host/Origin 门禁 | ❌ | `lib/request-security.ts` 对 IP 字面量直接放行（`127.0.0.1` 天然通过） |
| 原生模块 ABI（`node-pty`） | ❌ | 属**构建配置**问题（预构建可用性 / `@electron/rebuild` / 降级），不动上游源码 |
| Windows 路径大小写 / UNC | ❌ | 上游已有 `lib/paths.ts` 的 `toNativePath()`/`samePath()` 与 UNC 编解码 |
| 会话 HTML 导出（spawn `pi` CLI） | ❌ | 上游已有该路径（`app/api/sessions/[id]/export/route.ts`）；Electron 里 `process.execPath` 语义不同 ⚠️ → **登记为风险 R6，不改上游**，改用 API 参数/环境变量规避 |
| 通知事件源缺失 | ❌ | 采用会话 JSONL 尾随（零补丁）；不引入上游事件钩子 |
| 关闭语义（SSE 阻塞 `server.close()`） | ❌ | 上游 `instrumentation-node.ts` 已有处理；壳层只需在自己的退出链里按时序配合 |

**`patches/` 目录与 README 仍然建立**，写明「本版本为空」及其理由。**一旦某条潜在补丁真的需要**，必须同时登记「触发条件 / 实施时机 / 替代方案」并占用全局唯一编号（🔶 沿用 oc/dsh 的候选补丁登记规则），且遵守：① **幂等**（应用前先 `git apply --reverse --check`，成功即视为已应用 → 跳过）；② **冲突即终止**（绝不 `--3way` 强行合并，绝不覆盖 `../pi` 或 `../pi-web` 中的用户改动）；③ 新补丁不得落在既有补丁的连续上下文区间；④ 正反向往返须能 SHA-256 还原。

```
   → 复用 bin/rotate-preview-secrets.js 轮换预览密钥
   ⚠️ 裁剪必须在**副本**（pi-dist）上做，不要删源目录（🔶 沿用 HOS v1.1 的修正结论）

② smoke-desktop.mjs         （门禁：必须全绿才允许打包）
   用与 Electron 43.7.9 **同版本**的 Node（24.21.0）启动 Next 服务器：
   1) 断言 GET / 返回 SPA（含 Pi Web UI 标记）
   2) 断言 GET /api/web-auth 与一条带凭据的 /api/* 返回 200
   3) 断言 SSE /api/agent/[id]/events 可建连（text/event-stream）
   4) 断言 pi SDK 可创建 AgentSession（不调用模型）
   → 失败即**阻断流水线**

③ collect-pi.mjs            （组装产物）
   pi-dist/ = pi-web 产物（.next/** + public/** + next.config.ts + package.json + bin/）
            + node_modules/（@earendil-works/{pi-coding-agent,pi-agent-core,pi-ai,pi-tui} + 其余运行依赖）
            + config 预置模板（→ pi-agent/{settings.json,mcp.json,trust.json 默认值}）
   → tar -czf pi-dist.tar.gz --format=ustar
   → 写 SHA-256 marker（内容 = tar 包 SHA-256，**不是存在性判断**）

④ forge make                （打包）
   extraResource: ['pi-dist.tar.gz', 'resources/icon.png', 'resources/tray.png', ...]
   asar: true · executableName: 'pi-desktop' · icon: 'resources/icon'
   makers: Squirrel(win) / ZIP(win,mac,linux) / DMG(mac) / RPM(linux) / DEB(linux)
   ⚠️ prepackage/premake 钩子自动跑 ①→③（确保 `npm run make` 一条命令可复现）
```

### 8.4 开发/调试循环

- **壳层开发**：`npm start`（Forge + Vite），主进程热重载；渲染层为远程 URL，用 DevTools 调试。
- **服务端/UI 调试（摆脱打包往返）**：直接对 `../pi-web` 跑 `npm run dev`（`next dev -H 127.0.0.1 -p 30141`）或 `npm run build && npm start`，壳层加开关 `PI_DESKTOP_DEV_SERVER=http://127.0.0.1:30141` 直接加载它（跳过解压与内嵌服务器）。
- **主进程调试**：`--inspect`（**仅 dev**；生产构建必须移除，Fuses 已关 `EnableNodeCliInspectArguments`）；`openDevTools()` 仅 dev。
- **日志/诊断**：统一前缀 `[pi-desktop]`；`<userData>/logs/`；loading 页阶段文本；`globalThis.__hostError` 等诊断落点。
- **门禁**：`npm run typecheck`（strict TS）+ `node scripts/smoke-desktop.mjs` 是本地质量门；CI 同样以两者为准（🔶 沿用 dsh 的「脚手架阶段以 typecheck 为质量门」口径，本工程加上 smoke 门禁）。

## 9. 能力范围与降级

### 9.1 v1 In scope（必须达成）

1. 三平台安装包可安装启动，进入 **Pi Desktop** 窗口，无白屏、无闪退、无孤儿进程。
2. `pi-web` 服务端在主进程内就绪；`GET /` 返回 SPA；带凭据的 `/api/*` 通过。
3. **Pi Web UI 全功能可用**：会话列表/新建/重命名/导出、发消息、流式响应（SSE）、工具调用可视化、审批交互、上下文用量/成本、主题、多语言。
4. **会话持久化**：重启应用后会话仍在（JSONL → `~/.pi/agent/sessions/`）。
5. **模型与凭据配置**：Settings › Models 可登录（OAuth/API Key），与 `pi` CLI 共享 `auth.json`（Q6 默认共享）。
6. **工作目录选择**：可在应用内选定会话工作目录（沿上游 UI）。
7. **文件类工具可用**：读取/写入/编辑/列目录/图片附件。
8. **终端面板可用**（前提：`node-pty` 在 ABI 148 下可加载；否则降级并明示）。
9. **桌面壳能力生效**：托盘、原生通知（后台提醒）、单实例、窗口状态记忆、外链走系统浏览器、检查更新。
10. **构建可复现**：一条命令链从零产出三平台安装包，且 `smoke-desktop` 门禁全绿、`upstream.lock.json` 记录上游 SHA。

### 9.2 v1 Out of scope（二期+）

| 项 | 原因 | 计划 |
|---|---|---|
| 代码签名 / 公证 | 需要证书与 Apple 账号；不影响功能闭环 | Phase 3（§11.3） |
| 静默自动更新 | 依赖签名与更新生态 | 触发式（若启用，`RELEASES` 必须一并上传） |
| 深链 / 自定义协议 | 无明确需求；涉及跨平台注册细节 | Phase 2 评估 |
| 开机自启 / 全局快捷键 / 多窗口 | dsh 也明确暂缓 | Phase 2 评估 |
| 独立插件市场工程 | 上游 UI 已内置（Q7） | 不作为规划项 |
| 内置便携 Node/pnpm 运行时 | 无市场安装链路需要（桌面本就有 npm/git） | 不作为规划项 |
| 主 UI 的离线化（打包静态导出） | pi-web 不可静态导出 | 不作为规划项 |

## 11. 风险与开放问题

### 11.1 风险表

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| **R1** | **进程内 Next 使用了内部入口**（`next/dist/server/lib/start-server.js`），上游升级可能改变导出形态或行为 | 中（升级即可能失效） | ① 基线固定 tag（v0.11.1）；② 启动期做导出探测 + 明确报错（fail-visible）；③ 回退候选 B（sidecar）随时可切；④ 升级时把「内部入口复核」列入升级清单 |
| **R2** | **`node-pty` 在 Electron ABI 148 下不可加载** | 中（终端面板不可用） | P0-3 探针先行；可用则保留，不可用则 `@electron/rebuild`；仍不可用则**裁剪 + 明示降级**（终端非核心链路） |
| **R3** | **主进程内跑 Next 使主进程变重**（内存、事件循环、GC 与窗口管理相互影响） | 中 | 首启与交互延迟实测（⬜）；必要时把「会话 idle 超时」（`PI_WEB_IDLE_TIMEOUT_MS`，默认 600000）调低；极端情况切 sidecar |
| **R4** | **未签名安装包的用户体验**：Windows SmartScreen 警告、macOS Gatekeeper 拦截 | 中 | 文档明示（右键打开 / `xattr`）；Phase 3 签名决策（§11.3） |
| **R5** | **首启解压耗时**（数万文件）与中途失败 | 中 | marker 幂等 + 断点可重入（重新解压覆盖）；loading 页显示阶段与文件数；失败可见并给出「打开日志」 |
| **R6** | **会话 HTML 导出会 spawn `pi` CLI**：Electron 下 `process.execPath` 是 Electron 本体，行为与 Node CLI 不同 ⬜ | 中（导出功能可能失败） | P0 实测该路径；若不成立，按上游 API 参数/环境变量规避（不改上游）；必要时登记候选补丁 |
| **R7** | **`pi-web` 与 `pi` CLI 并发写同一会话 JSONL 不受支持**（上游 e2e 已注明） | 中（数据损坏） | Q6 的默认共享策略下，在 UI 提示与文档里明示「不要与 CLI 对同一会话并发写入」；提供「切到应用私有目录」的一键退路 |
| **R8** | **SSE 长期连接 + 主进程退出**：`server.close()` 可能挂住 | 中（退不干净） | 退出链按时序（关 SSE → close → deadline 强退），deadline = `PI_WEB_SHUTDOWN_DEADLINE_MS`（默认 5000） |
| **R9** | **更新检查的数据源未定**（GitHub API 有未认证限流） | 低 | 定义超时/失败静默降级（不阻塞、不误报）；数据源见 §11.3 |
| **R10** | **上游漂移**：`pi-web` 升级后 `bin/` 结构、认证算法、`request-security` 规则变化 | 中 | 基线 tag + 分支；本工程所有「上游机制」结论**带文件路径**；升级时逐条复核 |
| **R11** | **跨平台 CI 的一致性与时长**（三 OS × 完整构建） | 低 | `concurrency` 取消在途；缓存 npm；三平台各自构建各自产物；`fail-fast:false` |
| **R12** | **`pi-dist` 体积与安装包体积增长**（Electron ≈250 MB + pi-dist ≈116 MB 压缩） | 低 | 按目标平台裁剪原生件；剔除 `.next/cache`、devDependencies、非目标平台 prebuilds；⬜ 实测后定基线 |

## 12. 规格与文档体系

### 12.1 `specs/` 编号规范

```
specs/
├── README.md                 # 索引：模块清单 + 编号分配表 + 推荐阅读顺序
├── constitution.md           # 项目原则（架构/安全/IPC/代码质量/生命周期/流程）
├── ARCHITECTURE.md           # 整体架构（本文档 §4 的收敛版）
├── TECH.md                   # 技术选型与版本表
├── STRUCTURE.md              # 目录结构与进程入口表
├── overall-spec.md / overall-plan.md / overall-data-model.md
├── 0NN-<name>/               # 桌面壳基础模块（001–011，见 §6.4）
│   ├── spec.md               # 需求与验收（8 节骨架）
│   ├── plan.md               # 设计与实现方案（9 节骨架）
│   └── tasks.md              # 任务清单（可选；复杂模块才有）
└── 2NN-<name>/               # 扩展模块（201 起）
```

**硬规则**（🔶 沿用 dsh/oc）：
1. `spec.md` 与 `plan.md` **必须成对**（只交一半视为未完成）；目录名 `<NNN>-<kebab-name>`；编号**只增不改、不复用**。
2. 文档头统一：`> **Module:** … **Status:** … **Last Updated:** … **上游基线:** pi v1.1.0 / pi-web v0.11.1`；状态流转 Proposed → Accepted → Implementing → Implemented → Superseded。
3. **不留占位小节**：未定就写 `⬜` + 探针计划。
4. 需求条目编号 `FR-<module>-<三位数>`，用 MUST / MUST NOT / SHOULD / MAY 表述；**只追加不修订**（作废改标 `[SUPERSEDED by …]`）。
5. `plan.md` 必须回引 FR 编号（交叉引用表：FR → 代码位置）。
6. `spec.md` 骨架（8 节）：模块概述（目的/问题/范围）→ 用户故事 → 功能需求 → 关键实体 → 验收场景（Given/When/Then）→ 非功能需求 → 假设与约束 → 依赖。
7. `plan.md` 骨架（9 节）：技术上下文 → 宪法合规检查 → 研究结论（关键决策/源码级核实）→ 数据模型 → 接口契约 → 实现策略 → 测试考量 → 文件清单 → 与规格交叉引用。
8. **「源码即真理」**：每条声明可追溯到源码文件 + 行号；代码与文档冲突时，以代码为准并标注变更提示。
