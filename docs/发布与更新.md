## 1. 版本策略

### 1.1 单一版本源

| 项 | 规则 |
|---|---|
| **唯一版本源** | `package.json` 的 `"version"`（当前 **`0.1.0`**）。其它地方（应用内「关于」、产物名、tag、Release 标题）都从它推导，**不允许**各写一份 |
| **发布 tag** | `v<package.json version>`，例如 `v0.1.0`。tag 必须与 `package.json` 完全一致；不一致的 tag **不发版**（⬜ 一致性校验尚未在 `release.yml` 落地，见 §3 待办） |
| **触发关系** | 推 `v*` tag → `.github/workflows/release.yml` 构建三平台产物 → 汇总上传为 Release 资产（见 §3） |
| **版本递增语义** | `0.x` 阶段（Phase 0/1）：**minor 递增**（`0.1.0` → `0.2.0`…），用于「骨架/能力」里程碑；patch 用于修复。**`1.0.0` 在 Phase 1 出口判据（规划 §9.1 的 10 条）全部验收通过后**才允许打 |
| **预发布** | 需要试投放时用 `v0.x.y-rc.N`（GitHub 侧标 pre-release）；应用内「检查更新」对 pre-release 的取舍 ⬜ 待定（§5.4） |
| **不可变** | 已发布的 tag 与资产**不覆盖**：改错了发新版本；旧 Release 只允许追加说明（不得替换二进制） |

### 1.2 与上游版本的关系

| 项 | 规则 |
|---|---|
| 上游基线 | `pi` **v1.1.0** / `pi-web` **v0.11.1**，以 sibling 源码引用（`../pi`、`../pi-web`），并固定分支 `Branch_v1.1.0` / `Branch_v0.11.1` |
| 可复现锚点 | `node scripts/pin-upstream.mjs` 记录两侧 commit SHA → `upstream.lock.json`（⬜ 该文件当前被 `.gitignore` 忽略，见 §9 待办） |
| 上游升级 | **独立需求 + 独立 tag**：升级后必须重跑门禁（`npm run typecheck`、`node scripts/smoke-desktop.mjs`）、复核内部入口（规划 R1）与认证/轮换契约（R10），并在 `README.md` / 本文档更新「上游基线」 |
| Electron 版本 | `package.json` **精确钉住**（`43.7.9`，不用 `^`）；升级走独立需求（规划 §4.4） |

| 平台 | 期望形态（参考，**非实测**） |

## 2. 流水线（发布前置）

```bash
# ① 构建 pi-web 生产产物（../pi-web：npm ci → next build → 平台裁剪 → 轮换预览密钥）
node scripts/prepare-next.mjs

# ② 门禁：与运行时同版 Node（24.21.0）起服务，断言 SPA / 带凭据 API / SSE / pi SDK 建会话
node scripts/smoke-desktop.mjs

# ③ 组装 pi-dist（+ tar.gz(ustar) + SHA-256 marker）
node scripts/collect-pi.mjs

# ④ 打包 / 出安装包（premake 会自动重跑 ①→③，保证一条命令可复现）
npm run make            # 产物在 out/make/
npm run package         # 仅打包目录（含 pi-dist.tar.gz 与 resources/），不出安装包

# 辅助
npm run typecheck
node scripts/pin-upstream.mjs      # 记录 ../pi 与 ../pi-web 的 commit SHA
```

规则：

- **门禁不绿不许发布**：② 的四项断言任一失败即阻断（规划 §8.1）。
- **每个 runner 只构建自己平台的产物**：不做交叉打包（原生件必须与目标平台一致，规划 §8.5 踩坑 #8）。
- **裁剪只在副本上做**：不要删 `../pi-web` 源目录里的原生件（否则触发联网补下载，规划 §8.1 / HOS 踩坑）。
- **`pi-dist.tar.gz` + `pi-dist.version` 必须在包内**：由 `forge.config.ts` 的 `extraResource` 投放（含 `resources/icon.png`、`resources/tray.png`、`resources/trayTemplate.png`）。

## 3. CI 工作流

> **现状**：`ci.yml` 与 `release.yml` **已落地**（`.github/workflows/`）。下表按实际文件记录，并标出与规划 §8.5 形态的差异。

### 3.1 `.github/workflows/ci.yml`

| 项 | 内容 |
|---|---|
| 触发 | `push: branches: [main]` + `pull_request` + `workflow_dispatch` |
| 并发 | `concurrency.group: ci-${{ github.ref }}` + `cancel-in-progress: true`（取消在途） |
| 矩阵 | `[windows-latest, ubuntu-latest, macos-latest]`，`fail-fast: false` |
| 步骤（实际顺序） | ① `actions/checkout`（`path: pi-desktop`，即 checkout 到工作区**子目录**） → ② `git clone --depth 1 --branch $PI_REF $PI_REPO pi`、`git clone --depth 1 --branch $PI_WEB_REF $PI_WEB_REPO pi-web`（克隆到工作区**根**，与 `pi-desktop` 平级；用 `git clone` 而非跨仓库 `checkout path`） → ③ `actions/setup-node@v4` 固定 **24.21.0** + `cache: npm`（`cache-dependency-path: pi-desktop/package-lock.json`） → ④ Linux 装 `fakeroot`、`rpm` → ⑤ `npm ci` → ⑥ `npm run typecheck` → ⑦ `node scripts/pin-upstream.mjs` → ⑧ `node scripts/prepare-next.mjs` → ⑨ `node scripts/collect-pi.mjs` → ⑩ `node scripts/smoke-desktop.mjs` → ⑪ `npx --no-install electron-forge make` → ⑫ `actions/upload-artifact@v4`（`name: dist-${{ runner.os }}`、`path: pi-desktop/out/make/**`、`if-no-files-found: error`、保留 14 天） |
| 步骤（⚠️ 2026-10-13 更正，首跑后修正） | ② 的克隆改为**按上游 tag** 并断言 commit SHA：`git clone --depth 1 --branch v1.1.0 <pi-url> pi` + `test "$(git -C pi rev-parse HEAD)" = abe508e1…`（pi-web 同理 `v0.11.1` / `e7837219…`）——上游**没有** `Branch_v1.1.0`/`Branch_v0.11.1` 分支，用分支名克隆必然 `fatal: Remote branch … not found`；③ 与 ④ 之间新增「Ensure ffmpeg」（collect-pi 的品牌化需要它生成 web 位图图标；已装则跳过，缺失按平台 choco/brew/apt 安装） |
| 打包细节（Linux 必需） | `collect-pi` 的 tar 参数含 `--format=ustar --dereference`：ustar 的 linkname 字段上限 **100 字节**，而 POSIX 上 npm 会为 CLI 生成 `node_modules/**/bin/*` **符号链接**，深层嵌套下目标串超长会被 GNU tar 判为 `link name is too long; not dumped` 并以退出码 2 失败（Windows/macOS 的 bsdtar 不报错）。解引用后存为普通文件，内容与权限位不变；`pi-web` lockfile 无 `link:`/`file:` 依赖 ⇒ 不存在目录级符号链接 |
| 门禁 | `npm run typecheck` + `node scripts/smoke-desktop.mjs`（**显式步骤**） |
| 与规划的差异 | ① 规划 §8.5 写「`npm run make`」，实际用 `npx --no-install electron-forge make` —— **刻意绕过 npm 的 `premake` 钩子**，因为前置三步已在显式步骤里跑过，用钩子会重复执行一遍；② 实际执行顺序是 `prepare-next → collect-pi → smoke → make`（规划把 smoke 列在 collect 之前，结论不变：smoke 仍是**阻断项**） |
| 失败处置 | 任一 OS 失败 = 该提交不可合并进发布分支；三条矩阵**并行不受影响**（`fail-fast: false`） |

### 3.2 `.github/workflows/release.yml`

| 项 | 内容 |
|---|---|
| 触发 | `push: tags: ['v*']` + `workflow_dispatch`（带可选输入 `version`，留空则用 tag 名） |
| 权限/并发 | `permissions: contents: write`；`concurrency.group: release-${{ github.ref }}` + `cancel-in-progress: false`（发布**不允许**互相取消） |
| job 结构 | 两个 job：`build`（三 OS 矩阵，步骤与 §3.1 的 ⑤→⑫ 相同，artifact 名 `release-${{ runner.os }}`、保留 7 天）→ `release`（`needs: build`，`ubuntu-latest`） |
| 汇总 | `build` 各 OS 上传 `pi-desktop/out/make/**` → `release` job 用 `actions/download-artifact@v4`（`merge-multiple: true`）合并 → `chmod -R +x artifacts`（保住 Linux/macOS 资产的可执行位）→ `find` 打印资产清单 |
| 上传 | `softprops/action-gh-release@v2`：`tag_name: ${{ inputs.version || github.ref_name }}`、`fail_on_unmatched_files: false`、`generate_release_notes: true`；上传 `*.exe`、`*.nupkg`、`RELEASES`、`*.zip`、`*.dmg`、`*.deb`、`*.rpm` |
| 必需项 | Windows 侧 **`RELEASES` 与 `.nupkg` 必须一并上传**（已包含在上传 glob 内；将来启用 Squirrel 自动更新时缺它们会无法增量） |
| 发布说明 | `generate_release_notes: true` + 工作流内置固定 `body`：三平台安装方式（含未签名的 SmartScreen / 右键打开 / `xattr` 指引，与 §4.2 一致）、**升级无需手动清理**（首次启动校验 `pi-dist` 归档 SHA-256，不一致即重新解压）、以及「不签名 + 不静默更新」声明。⬜ 仍需人工补：上游基线（`pi`/`pi-web` tag + SHA）与已知限制（指向 `docs/桌面能力清单.md`） |
| 不做 | 不上架商店、不签名、不公证；不覆盖既有 Release 资产 |

### 3.3 平台踩坑清单（实现 CI 时逐条对照）

| # | 事项 |
|---|---|
| 1 | 上游用 `git clone --branch <固定分支> --depth 1` 到平级目录，并记录 SHA；不要用跨仓库 checkout |
| 2 | 若将来产生补丁文件：UTF-8 + `.gitattributes` 强制 `*.patch text eol=lf`（CRLF 会让 `git apply` 失败；本仓库 `.gitattributes` 已备好） |
| 3 | Linux 的 rpm 打包会 strip 二进制：**跨平台原生件必须先按目标平台裁剪**，否则 arm64 的 `.node` 被误伤 |
| 4 | Windows Squirrel 的 `RELEASES` 与 `.nupkg` 必须一起上传 |
| 5 | `executableName: 'pi-desktop'`（已配），Linux maker 的包名与可执行名要对得上 |
| 6 | macOS 未签名 DMG：发布说明必须写「右键打开」与 `xattr -dr com.apple.quarantine` |
| 7 | Electron 二进制下载慢：CI/本地可设 `ELECTRON_MIRROR` |
| 8 | 三平台各自构建各自产物，**不交叉打包** |

### 4.2 未签名安装包的用户指引（必须出现在 Release 说明与官网下载页）

**Windows（SmartScreen）**

1. 双击 `Pi Desktop-<version> Setup.exe`。
2. 若出现「Windows 已保护你的电脑」→ **更多信息** → **仍要运行**。
   （原因是安装包未做代码签名，不是检测到病毒。）
3. 安装完成后从开始菜单启动 `Pi Desktop`；卸载走「设置 → 应用 → 已安装的应用」。
4. 若企业环境用组策略拦截未签名程序：需管理员放行或改用 `.zip` 解压后运行（⬜ 该场景未实测）。
5. **卸载行为与残留（2026-10-13 轮次 2 实测）**：Squirrel 的 `Update.exe --uninstall` 会移除注册表项（`Pi Desktop`）并停止/清理应用，但**保留安装根** `%LOCALAPPDATA%\pi_desktop`（`Update.exe` + `.dead` + `app-<ver>` 壳目录，实测残留 `squirrel.exe` 与 `v8_context_snapshot.bin` 共 ≈2.7 MB）。要「彻底卸载」需手工删除该目录；`<userData>`（`%APPDATA%\Pi Desktop`，含解压后的 `pi-dist` 与 `pi-dist.sha256`）按设计**保留**，如需清理请一并删除。⚠️ 与「设置 → 应用」卸载同源，两条路径行为一致。

**macOS（Gatekeeper）**

1. 打开 `.dmg`，把 `Pi Desktop` 拖进 `Applications`。
2. **首次启动不要双击**（未签名会被拦）：在 `Applications` 里 **右键 → 打开 → 打开**；
   或先移除隔离属性：

```bash
sudo xattr -dr com.apple.quarantine "/Applications/Pi Desktop.app"
open -a "Pi Desktop"
```

3. 若提示「已损坏，无法打开」：同样是隔离属性导致，用上面的 `xattr` 命令处理（不是文件真的损坏）。
4. 卸载：把 `Applications/Pi Desktop.app` 拖入废纸篓；用户数据按需清理（见 §6.3）。

**Linux**

```bash
# Debian / Ubuntu
sudo apt install ./pi-desktop_<version>_<arch>.deb
# Fedora / RHEL
sudo dnf install ./pi-desktop-<version>.<arch>.rpm      # 或：sudo rpm -i ...
# 免安装（zip）
unzip "Pi Desktop-<version>-linux-<arch>.zip" -d pi-desktop && ./pi-desktop/pi-desktop
```

> Linux 无强制签名门禁，但部分发行版对 `.rpm` 默认开启 GPG 校验；未签名包的提示与放行方式 ⬜ 未实测。

**首启预期（三平台一致）**：首次启动会解压 `pi-dist.tar.gz`（数万文件），loading 页会显示阶段与进度；
**解压期间不要强杀进程**（会留下不完整目录，下次启动会自动重新解压）。首启耗时 ⬜ 未测量（P0-4）。

## 5. 应用内「检查更新 → 引导下载」

### 5.1 行为（已决策 Q5 = 半自动）

| 步 | 行为 |
|---|---|
| 1 | 入口：应用菜单 / 托盘 / 「关于」页的「检查更新」 |
| 2 | 查询更新源（超时 **8 s**），得到最新版本号与更新说明链接 |
| 3 | 与当前版本（`package.json.version`）做**语义化版本比较** |
| 4 | 有新版 → 弹窗展示版本号 + 更新说明链接 → 点击 `shell.openExternal(<下载页>)` 打开**系统浏览器** |
| 5 | 无新版 → 提示「已是最新版本」 |
| 6 | 失败（网络不可达 / 限流 / 解析失败）→ 提示「无法检查更新」+ 写日志，**不阻塞、不误报**（规划 R9） |
| **不做** | 不自动下载、不静默安装、不在应用内下载二进制（明确登记，见 §7） |

补充：壳层启动时置 `PI_WEB_SKIP_VERSION_CHECK=1`，让**上游自带的**版本提示闭嘴，
避免「两套升级提示」互相打脸；升级提示只由本工程这一处负责。

### 5.2 两个候选数据源（⬜ 待定，规划 §11.3#2）

| 候选 | 形态 | 优点 | 风险/成本 |
|---|---|---|---|
| **A. GitHub Releases API** | `GET https://api.github.com/repos/fellow99/pi-desktop/releases/latest` | 零额外基建；与发布流水线同源 | **未认证限流**（每 IP 每小时数十次）；返回体大；企业代理环境可能不可达；解析 `tag_name`/`assets` 需容错 |
| **B. `pi-desktop-website` 静态 feed** | 官网（同级 `../pi-desktop-website`，规划中）提供的静态 JSON（如 `/releases.json`） | 可带自定义字段（下载页 URL、最低支持版本、渠道）；不限流；可离源站做 CDN | 需维护官网工程与产物；数据需与 Release 同步（漏更新就会误报） |

**当前实现取向**：默认值取 **A**（`src/main/constants.ts` 的 `DEFAULT_UPDATE_FEED`），并提供环境变量覆盖以便接 B（切官网 feed 时不需要改代码）。
**结论仍为 ⬜**：最终数据源（A / B / A 主 B 备）须由 §11.3#2 的人工决策定稿；定稿后回填本节与 `README.md`。

## 6. 升级语义（`pi-dist` 重解压规则）

### 6.1 产物与 marker

| 项 | 值 |
|---|---|
| 包内归档 | `<resources>/pi-dist.tar.gz`（`--format=ustar`，运行时用 `createGunzip` **流式**解压，固定内存） |
| 包内期望值 | `<resources>/pi-dist.version` —— 归档的 SHA-256（构建期由 `collect-pi.mjs` 写入） |
| 解压目标 | `<userData>/pi-dist/` |
| 幂等 marker | `<userData>/pi-dist.sha256`（内容 = **已解压归档**的 SHA-256） |
| 判据 | `marker === pi-dist.version` → **跳过解压**（仍会校验负载完整性）；**不相等 → 删除旧目录后重新解压** |

### 6.2 三种情形（判定与动作）

| 情形 | 判定 | 动作 |
|---|---|---|
| 升级（换包/换版本） | 归档内容变了 → `pi-dist.version` 变化 → marker 不一致 | `rm -rf <userData>/pi-dist` → 重新解压 → 重写 marker（**不残留旧文件**） |
| 同版本再启动 | marker === 期望值 | **不再解压**（快路径）；但仍断言 Next 入口与 `@earendil-works/pi-coding-agent` 存在 |
| 上次解压被中断 | marker 缺失，或 marker 一致但缺关键入口 | **强制重新解压**（可重入；旧目录先清理） |

> ⚠️ **绝不允许**把判据退化成「目录存在即跳过」：那会让就地升级不生效（参考工程真机踩过这个坑）。
> ⚠️ **计划文档与实现的差异**：`docs/工程规划.md` §4.6/§8.3 把 marker 写作 `pi-dist/.pi-dist.sha256`，
> 实现放在 `<userData>/pi-dist.sha256`（不污染解压目录）。以**代码为准**（`src/main/artifact.ts`、`src/main/constants.ts`），
> 本轮以文档记录该差异，不改代码、不擅自改规划。

### 6.3 升级时不动的东西（用户数据）

| 路径 | 升级时行为 |
|---|---|
| `~/.pi/agent/`（默认共享数据目录：`settings.json`、`auth.json`、`mcp.json`、`sessions/`、`extensions/`、`skills/`…） | **不删不改**；预置模板只在文件**不存在**时写入（绝不覆盖用户改动） |
| `<userData>/pi-agent/`（`agentDirMode: 'app'` 时） | 同上 |
| `<userData>/pi-desktop-settings.json` | 不参与重解压，保留（`agentDirMode` 等） |
| `<userData>/window-state.json` | 保留 |
| `<userData>/logs/` | 追加，不清理（⬜ 是否需要保留策略/轮转，未定） |

**发布说明必须写清**：跨大版本升级时，`pi-dist` 会**重新解压**（首启耗时会回到首次启动的量级）；
用户数据不动；若用户在共享模式下与 `pi` CLI 并用，不要对同一会话并发写入（上游不支持，规划 R7）。

### 6.4 开发态旁路（仅开发）

## 7. 明确不做（登记理由与复议时点）

| 项 | 决定 | 登记理由 | 复议时点 |
|---|---|---|---|
| **代码签名** | 不做 | 需 Windows 代码签名证书与采购流程；不影响功能闭环；未签名的影响可被文档化的用户指引覆盖（§4.2） | **Phase 3**（规划 §11.3#3）；触发条件：出现真实分发渠道要求或用户投诉量上升 |
| **Apple 公证（notarization）** | 不做 | 需 Apple Developer 账号 + `notarytool` 流水线；与签名同批决策才划算 | **Phase 3**（同上） |
| **静默自动更新** | 不做 | 依赖签名与更新生态；未签名自动更新会在客户端出现不可解释的失败；且会与「检查更新」形成两套提示 | **触发式**：由 Phase 3 评估；若启用，**`RELEASES` 必须与 `.nupkg` 一并上传**（现在就按此要求上传，避免届时补账） |
| **深链 / 自定义协议** | 不做 | 无明确需求；涉及三平台注册细节（`.desktop`/Info.plist/注册表） | **Phase 2**（规划 §5.8 / §9.2） |
| **开机自启 / 全局快捷键 / 多窗口** | 不做 | 与 dsh 同款取舍；关窗即退出是 v1 的既定行为 | **Phase 2** |
| **独立插件市场工程** | 不做 | 上游 UI 已内置 Plugins/Skills/MCP 管理（Q7），自建属重复建设 | 不列入规划 |
| **交叉打包** | 不做 | 原生件（`node-pty` / SWC）必须与目标平台一致；交叉包风险高于收益 | 若 CI 成本成为问题再评估 |
| **应用内下载/安装更新包** | 不做 | 与静默更新同批决策；应用内下载还会带来校验、断点、代理等一整套问题 | Phase 3 |
