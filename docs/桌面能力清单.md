## B. 降级矩阵（能力 → 触发条件 → 降级行为 → 用户可见性）

**总原则**：**fail-visible** —— 不允许「卡住但不说」，也不允许静默降级（规划 §3 原则 5）。
所有降级都必须同时满足：① loading 页/界面显示具体阶段与原因；② 落 `<userData>/logs/pi-desktop-*.log`（前缀 `[pi-desktop]`）。

| 能力 | 主路径 | 降级触发条件 | 降级后的行为 | 可见性载体 |
|---|---|---|---|---|
| 进程内 Next 宿主 | 候选 A：`node_modules/next/dist/server/lib/start-server.js` 的 `startServer({dir,hostname,port})` | 导出探测失败（文件缺失 / 无 `startServer` / 调用抛错） | 候选 A′：`node_modules/next/dist/server/next.js` 的 NextServer 自定义服务器 API（**仍进程内**）；再失败则 ⬜ 走候选 B | 日志 + loading 页阶段文本（`src/main/host.ts` 逐候选记录 `tried` 原因） |
| 进程内 Next 宿主（B 档） | — | `PI_DESKTOP_HOST_MODE=spawn`（**只显式开启，不自动兜底**）或 A/A′ 均失败后的专项决策 | sidecar `next start`（`ELECTRON_RUN_AS_NODE=1`）+ 进程树清理（Windows `taskkill /T /F`） | 日志（`PI_DESKTOP_HOST_MODE=spawn` 警告 + sidecar 输出转发） |
| 终端 / PTY | `node-pty` 在 ABI 148 下直接加载 | 加载失败（缺 prebuild / ABI 不匹配 / `@electron/rebuild` 仍失败） | 按规划 R2 三段处置：① 用预构建；② `@electron/rebuild` 按 ABI 148 重编；③ **裁剪 + 终端面板明示降级**（终端非核心链路） | 界面明示 + 日志（⬜ 具体文案在 P0-3 定稿） |
| 密钥轮换（预览密钥） | `require(<pi-dist>/bin/rotate-preview-secrets.js)` 后调用 | 脚本缺失 / 未导出 `rotatePreviewSecrets` / `pi-dist` 不可写 | **不静默**：脚本缺失即抛错（fail-visible）；执行失败按上游告警打印（`getRotationWarning`），保留已发布密钥 | 日志警告 + 启动阶段；`docs/工程规划.md` §4.2 步骤 3 |
| 产物就位（`pi-dist`） | marker（SHA-256）命中且 `assertPayloadComplete` 通过 → 跳过解压 | 归档缺失 / marker 不一致（升级或换包）/ marker 一致但缺 Next 入口或 `@earendil-works/pi-coding-agent` | 清理旧目录后**重新解压**（幂等，可重入） | 归档缺失时错误里直接给出补救命令（`node scripts/prepare-next.mjs && node scripts/collect-pi.mjs`，或设 `PI_DESKTOP_PI_DIST`） |
| 内容搜索（`rg`/`fd`） | 系统已有或上游下载 | 离线 / 下载被拒 | 搜索类工具不可用（上游行为），需用户改用其它方式 | ⬜ 待实测确认上游是否给出可见提示（P0-3） |
| `git` / worktree | 用户机有 `git` | 无 `git` | 上游自动降级（worktree/diff/文件树不回错） | ⚠️ 上游是**静默**降级 → 本工程需在 UI/日志补可见性（⬜ 方案在 P0-3 定稿） |
| 平台通知 | 系统通知中心 | 通知权限被拒 / 桌面环境无通知服务 | 应用内不阻塞；托盘与界面仍在 | 日志 |
| 托盘 | 单例 `Tray` | 图标资源缺失 / 平台不支持 | 菜单项按就绪态**禁用而非消失**（沿用 dsh 现状） | 日志 |

## C. 与鸿蒙版（`pi-desktop-hos`）的能力差异

`pi-desktop-hos` 的结论是它**自己真机实测**的结果（原文见 `../pi-desktop-hos/docs/工程规划.md` §9.3、`../pi-desktop-hos/docs/鸿蒙环境能力清单-v0.11.1.md`、`../pi-desktop-hos/docs/真机验证记录.md`）。
下表左列一律按 `🔶 沿用` 处理：**不得**当成本工程实测事实；右列是本工程的**判定**（未测一律 ⬜）。

| 能力 | `pi-desktop-hos`（鸿蒙，v0.11.1 实测，🔶） | 本工程（桌面，Windows/macOS/Linux） | 差异根因 / 依据 |
|---|---|---|---|
| 终端 / PTY | ❌ 不可用（`node-pty` 无 `openharmony-arm64` 产物；`require` 即失败） | ✅ **可用**（轮次 2：修复本机不完整的 prebuilds 后 R7 通过；根因见 §A#1 与 §E.2 的更正） | HOS 是**L2 原生产物缺失**；桌面 Windows 是**本机安装不完整的空壳 prebuilds**（上游发布包含 x64 产物），已修并加构建期守卫 `FR-010-027` | ✅ 已由 P0-3（轮次 1 → 轮次 2）定论 |
| `bash` 工具（命令执行） | ⚠️ 需壳扩展顶替（真相：子进程 `exit/close` **永不送达**，工具会永久挂住） | ⬜ **原生可用预期** | HOS 是平台子进程机制问题（L1）；`决策` 桌面子进程事件正常送达（规划 §9.3） |
| MCP stdio 服务器 | ⚠️ 降级（继承「子进程不可靠」） | ⬜ **恢复预期** | 同上 |
| OAuth 回环登录 | ⚠️ 冲突（难以承载回环回调） | ⬜ **恢复预期** | 桌面 loopback 可用；上游 OAuth 本就按本地回调设计 |
| `git` / worktree | ❌ 不可用（设备无 `git` 二进制） | ⬜ 可用（依赖用户机有 `git`，缺失时上游降级） | HOS 是 L2（无二进制）；桌面取决于用户环境 |
| 内容搜索 `rg`/`fd` | ❌ 降级（无二进制且离线禁下载） | ⚠️ 条件可用 | 桌面可下载/可预装；离线仍不可用 |
| 扩展/技能在线安装 | ❌ PL1「仅本地源」+ `PI_OFFLINE=1` | ⚠️ 条件可用（需 `npm`/`git` + 网络） | 桌面有包管理器与网络；`PI_OFFLINE` 保留为可选开关 |
| 符号链接 / `chmod` / `/tmp` | ❌ 受限（symlink `EACCES`、`chmod` 被改写、`/tmp` 不可写） | ⬜ **正常预期** | 桌面无沙箱（规划 §2.4 / §4.6） |

### E.2 本机观测（Phase 0 前的一次性核对，2026-10-12）

```bash
cd /d/pi-workspace
git -C pi describe --tags --always      # v1.1.0（branch: Branch_v1.1.0）
git -C pi-web describe --tags --always  # v0.11.1（branch: Branch_v0.11.1）
ls -1 pi-web/node_modules/next/dist/server/lib/start-server.js   # 存在（24,909 B）
find pi-web/node_modules/node-pty/prebuilds -maxdepth 4
# 目录：darwin-arm64 / darwin-x64 / linux-arm64 / linux-x64 / win32-arm64 / win32-x64
# 文件仅 9 个：darwin-arm64/{pty.node,spawn-helper}、linux-arm64/pty.node、
#              win32-arm64/{conpty.node,conpty_console_list.node,conpty/*.dll,OpenConsole.exe,*.pdb}
# ⚠️ darwin-x64 / linux-x64 为空目录；win32-x64 下只有一个空的 conpty/ 目录
ls -d pi/node_modules   # 不存在（../pi 的 npm install 尚未执行）
```

**这些观测怎么用**：平台目录名存在 → 支持「上游按平台分发 prebuild」这一事实；
**x64 目录为空是「本机环境现状」，不能直接推断「上游 tarball 缺 x64 产物」**
（可能是本机安装不完整）。因此 **ABI 148 可加载性、以及 Windows x64 是否真的没有可用 prebuild，
必须在干净 `npm ci` 后由 P0-3 定论**。在此之前，终端/PTY 一律 ⬜。

> **P0-3 定论（2026-10-13；轮次 1 初判 → 轮次 2 更正）**：Windows 上 `node-pty` 起初**确实无法加载**，但根因不是「上游缺件」：
> 上游 npm 发布包 `node-pty-1.2.0-beta.15.tgz` **内含** `prebuilds/win32-x64/{conpty.node, conpty_console_list.node, conpty/{conpty.dll,OpenConsole.exe}, *.pdb}`（6 条目，已逐项 sha256 与恢复后的文件核对相等）；
> 是**本机 `node_modules` 安装不完整**（`prebuilds/win32-x64/` 只剩空壳 `conpty/`），而上游 `scripts/prebuild.js` 只判断该目录**是否存在** ⇒ 误判「已预构建」⇒ 跳过 `node-gyp rebuild`。
> 修复：按发布包恢复预构建（等价做法 `npm_config_build_from_source=true npm rebuild node-pty`），PTY 随即可用（R7 通过，见 §A#1）；
> 并把该坑做成**构建期硬失败**（`FR-010-027`：`scripts/prepare-next.mjs` 的 `verifyNativeDeps()`，空壳即失败并给出修法）。
> 证据：`logs/20261013-0/{13-probe-renderer.log（R1–R6 PASS / R7 FAIL）,18-package-pty.log,21-probe-renderer.log（PASS）,22-p05-notify.log（PASS；首轮 19 为 1 PASS / 4 FAIL）}`、`evidence/17-native-deps-negative.log`。
